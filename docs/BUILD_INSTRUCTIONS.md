# X Automation — Claude Code 전체 구현 지시서

대상 저장소: https://github.com/yuntyu01/x-automation  
작성일: 2026-10-27  
목표: 1인 운영자가 콘텐츠 생성·편집·이미지 준비·예약·X 본문과 자기 답글 게시를 관리하는, **모바일 앱처럼 사용하는 반응형 웹**을 완성한다.

이 문서는 기획 메모가 아니라 구현 명령이다. 전체를 읽고 아래 14단계를 순서대로 수행하라. 기존 코드가 있으면 조사한 뒤 충족된 항목은 검증하고 나머지를 구현한다. 이 문서 작성 시 저장소는 비어 있었다. 실행 시점의 실제 저장소 상태가 우선이다.

## 1. Claude Code 실행 계약

### 1.1 작업 방식

1. 저장소의 AGENTS.md, CLAUDE.md, README, 이 문서와 기존 코드를 먼저 읽는다. 이후 CLAUDE.md에는 이 문서와 진행 기록을 읽도록 짧게 연결한다.
2. **계획을 말한 뒤 멈추지 말고 구현·검증·수정·커밋·푸시까지 실행한다.**
3. 매 단계 완료 시 아래 형식으로 보고하고, “다음 단계 진행할까요?”를 묻지 않고 바로 계속한다.
4. 판단 가능한 기술 선택·UI 세부·파일 구조는 직접 결정하고 이유를 기록한다. 사용자에게 확정된 요구사항을 다시 묻지 않는다.
5. 외부 API 키나 실제 배포 권한이 없어도 실제 어댑터 코드, 로컬 실행, 목업 통합 테스트, UI, 배포 문서까지 구현한다. 실제 연결 검증만 미검증으로 남긴다.
6. 목업 성공을 실제 X 게시·R2 저장·유료 AI 생성 성공으로 보고하지 않는다. 핵심 기능을 TODO, 가짜 성공 응답, 화면만 있는 버튼으로 끝내지 않는다.
7. docs/PROGRESS.md에 단계별 상태·검증·차단 요인·다음 작업을 기록한다. 컨텍스트가 줄거나 세션이 재개되면 이 파일을 읽고 미완료 단계부터 이어간다.
8. 실제 도구의 승인·권한 제한은 우회하지 않는다. 접근 불가 항목은 원인을 기록하고 독립적인 작업을 모두 끝낸 다음 남은 외부 설정을 한 번에 보고한다.
9. 요청한 기능은 전부 구현 범위다. “MVP니까 제외”라는 이유로 생략하지 않는다. 15절의 확장 후보만 후속 범위로 구분한다.
10. 모든 사용자 화면·오류·도움말은 한국어를 기본으로 한다. 코드 식별자는 일관된 영어를 사용한다.

단계 보고 예시:

~~~text
[04/14 단계 완료] 모바일 앱 셸·공통 컴포넌트·테마 구현
검증: 390px/1440px 레이아웃, 키보드 탐색, 프론트 빌드 통과
커밋: <실제 SHA> — feat(ui): add responsive app shell and themes
푸시: origin/main 반영 확인
다음: 콘텐츠 보관함과 프롬프트 편집 구현
~~~

### 1.2 main 커밋·푸시

사용자는 이 저장소의 **main에 단계별로 커밋·푸시**하는 것을 요청했다. 별도 PR 승인을 기본 절차로 추가하지 않는다.

- 시작할 때 원격 URL, 현재 브랜치, 작업 트리, 원격 main 상태를 확인한다.
- 다른 저장소에 작업하지 않는다. 기존 미커밋 변경과 사용자 작업을 보존한다.
- 각 단계의 관련 검증이 통과하면 해당 변경만 스테이징하고 의미 있는 커밋을 만든 뒤 origin/main에 푸시한다.
- 푸시 전 원격 변경을 확인하고 안전하게 통합한다. 충돌은 내용을 검토해 해결하고 관련 검증을 다시 수행한다.
- 강제 푸시, 공유 이력 재작성, 무단 reset --hard, 브랜치 보호 우회, 기존 데이터 삭제를 하지 않는다.
- 비밀정보, .env, DB 덤프, 실제 사용자 콘텐츠, 실제 토큰이 든 테스트 산출물을 커밋하지 않는다.
- Git 인증·브랜치 보호 때문에 푸시할 수 없다면 가능한 구현과 로컬 커밋을 계속하고 미푸시 커밋 목록을 기록한다. 성공했다고 쓰지 않는다.
- 마지막에는 원격 main의 커밋과 파일을 확인한다. 최종 보고에는 단계 완료 수, 실제 검증, 남은 외부 설정, 마지막 커밋 SHA를 포함한다.
- 단계 커밋에는 진행 기록을 포함한다. 현재 커밋의 SHA를 같은 커밋 안에 넣으려 하지 말고 보고 또는 다음 진행 기록에 적는다.

### 1.3 개발과 운영 시작 구분

구현 검증은 격리된 테스트 DB·목업·테스트용 저장소로 수행한다. 개발 중 실제 X에 테스트 글을 게시하거나 유료 서비스를 구매하지 않는다.

실서비스 자동 게시에는 다음 조건이 모두 필요하다.

- 운영 환경의 PUBLISHING_ENABLED=true
- 실제 X 연결 및 필요한 설정 완료
- 사용자가 앱에서 “자동 운영 시작” 실행
- 해당 예약의 콘텐츠·이미지·검토·시간·예산 조건 충족

처음 배포한 앱의 자동 운영 상태는 꺼짐이다. 사용자가 켠 이후의 상태는 DB에 보존하며 재배포 때 임의로 초기화하지 않는다. 환경변수 스위치는 운영자가 전체 실게시를 막는 별도 차단 장치다. UI에는 어떤 조건 때문에 게시가 비활성인지 명확히 표시한다.

## 2. 제품 범위와 초기 설정

### 2.1 확정 요구사항

| 항목 | 구현 요구 |
|---|---|
| 사용자 | 지정한 관리자 한 명. 회원가입·다중 사용자·다중 조직 없음 |
| X 계정 | 최초 한 계정 연결 |
| 기술 | Go + PostgreSQL + R2. Go 서버 하나가 프론트와 API 제공 |
| 배포 | KoDeploy에 배포할 수 있는 컨테이너와 설정 문서 |
| 콘텐츠 | 소설·썰·명언 등 기존 프롬프트 활용, 직접 입력도 지원 |
| 게시량 | 기본 하루 20묶음, 앱에서 변경 |
| 답글 | 기본 본문 1개 + 자기 답글 1개, 분량 초과 시 추가 답글 |
| 이미지 | AI 생성·직접 업로드·이미지 없음 선택 |
| 운영 | 완전 자동 / 검토 후 게시 / 게시만 자동 |
| 자동 게시 시간 | 새벽과 낮의 복수 구간. 아침·저녁은 사용자가 직접 운영 |
| 간격 | 기본 30분 + 사용자가 정한 범위의 추가 랜덤 지연 |
| 생성 시점 | 게시 시각에 생성 / 버튼 생성 / 자동 사전 생성 |
| 알림 | 앱 내부 알림만 |
| 이미지 보관 | 실제 게시된 이미지의 마지막 게시 완료 후 14일 경과 시 정리 |
| 디자인 | 토스 UX의 쉬운 흐름, 제공된 modo 화면의 여백·카드·타이포 참고 |
| 화면 | 모바일 앱 같은 웹, PC 대응, 라이트·다크·시스템 테마 |

**20묶음은 X 게시물 20개가 아니다.** 본문과 답글 하나로 구성한 20묶음은 X 게시물 40개다. 추가 분할되면 더 늘어난다. 목록·예산·예약에서 묶음 수와 실제 게시물 수를 구분한다.

타인의 댓글을 읽고 자동 답변하는 기능, 자동 좋아요·팔로우, 커뮤니티 글 자동 수집은 범위가 아니다. 사용자는 자기 글의 후반부를 답글로 이어 게시하기만 원한다. 아침·저녁에 X에서 직접 올린 글을 이 앱이 수집하거나 변경하지 않는다.

### 2.2 변경 가능한 예시 기본값

아래 시각·세부 수치는 설계 예시이며 사용자 확정값처럼 하드코딩하지 않는다. 첫 설정에서 수정할 수 있고, 자동 운영 시작 전에 실제 설정을 보여준다.

| 설정 | 제안 초기값 |
|---|---|
| 시간대 | Asia/Seoul |
| 허용 구간 | 새벽 00:00~06:00, 낮 12:00~17:00 |
| 추가 지연 | 0~5분 |
| 기본 생성 전략 | 매일 21:00에 다음 날 부족분 준비 |
| 예약 전 생성 대안 | 예약 30분 전 |
| 재고 보충 대안 | 준비 수량 5개 미만이면 목표 20개까지 |
| 이미지 | AI 이미지 사용 선택, 묶음당 1장부터, 위치 변경 가능 |
| 본문→답글 간격 | 본문 성공 확인 후 이어 게시. 별도 지연을 설정할 수 있음 |
| 보관 기간 | 게시 후 14일 |
| 월 비용 한도 | 금액을 임의 확정하지 않음. 선택적 설정 제공 |

운영 모드, 생성 방식, 모델, 이미지 사용, 게시량, 시간 구간, 간격, 추가 지연, 답글 구성, 보관 기간, 예산 정책은 앱에서 바꿀 수 있어야 한다. 서버 비밀값·인증용 설정은 서버 환경변수 또는 Secret으로 관리한다.

## 3. 콘텐츠와 프롬프트

### 3.1 콘텐츠 묶음

하나의 묶음은 다음을 연결한다.

- 관리용 제목·카테고리·태그·작성 출처
- 분할 전 원문과 수정 이력
- 본문 및 순서가 있는 자기 답글
- 각 게시 부분의 이미지·대체 텍스트·순서
- 사용한 프롬프트 버전·모델·생성 옵션
- 생성 상태와 검토 상태
- 예약 시각·고정 여부·예약 실행 기록
- 부분별 실제 X 게시 ID·URL·성공 시각·오류
- 예상 비용과 확인 가능한 사용량

생성 상태, 검토 상태, 예약 상태, 게시 결과를 하나의 거대한 status에 섞지 않는다. 이미 게시한 revision은 불변 기록으로 남기고 이후 편집은 새 revision으로 보관한다.

### 3.2 보관함과 편집

- 작성 중·검토 대기·준비 완료·예약·게시 완료·문제 발생 필터.
- 카테고리, 제목·원문 검색, 기간 필터, 정렬과 페이지네이션.
- 텍스트 붙여넣기, 본문·답글 직접 입력, 여러 콘텐츠 일괄 등록.
- CSV·JSON 가져오기 양식 다운로드, 필드 매핑·오류 행·등록 전 미리보기.
- JSON·CSV 내보내기. 줄바꿈·한글을 보존하고 스프레드시트 수식 실행 위험을 처리한다. 자격증명은 내보내지 않는다.
- 자동 저장과 “저장 중/저장됨/저장 실패” 상태, 충돌 감지, 수정 되돌리기.
- 본문·답글 추가, 순서 변경, 분할 위치 수정, 각 부분 복사, 전체 복사.
- 실제 X 타래에 가까운 미리보기와 각 부분의 길이·이미지·순서 표시.
- 복제, 분류 변경, 보관, 여러 건 선택, 일괄 예약·예약 취소·내일로 이동.
- 게시 완료 카드에 X에서 보기, 게시 시각, 부분별 결과, 이미지 정리 상태.
- 앱의 보관·삭제는 X 게시물 삭제와 다르다. 기본 기능으로 실제 X 게시물을 자동 삭제하지 않는다.
- 원문을 자동으로 지우거나 게시 완료 후 6시간 만에 데이터 전체를 삭제하지 않는다. 참고 사진의 “6시간 뒤 보드에서 제거”는 최종 요구가 아니다.

### 3.3 프롬프트

- 기존 프롬프트를 그대로 붙여넣어 등록·수정·복제·비활성화한다.
- 카테고리별 프롬프트, 이름, 설명, 변수, 기본 모델·길이·말투·이미지 옵션.
- 주제·말투·길이 등의 변수는 구조화된 입력으로 제공하며 유효성 검사한다.
- 변경 이력을 남기고 어떤 버전으로 생성했는지 추적한다.
- 프롬프트 변경은 이후 생성에 적용한다. 이미 만들어진 콘텐츠를 몰래 다시 생성하지 않는다.
- “짧게”, “말투 변경” 등 수정 요청, 본문·답글·이미지 부분 재생성.
- 재생성 전 현재 편집 내용을 보존하고 결과를 비교·적용할 수 있게 한다.
- 사용자가 아직 프롬프트를 입력하지 않았다면 입력 필요 상태를 보여준다. 실제 사용자가 완성한 프롬프트를 임의로 알고 있다고 가정하지 않는다.
- 예제 프롬프트·데모 콘텐츠에는 예시라는 표시를 한다.

## 4. 생성과 운영 모드

### 4.1 운영 모드

| 모드 | 동작 |
|---|---|
| 완전 자동 | 프롬프트·옵션에 맞게 준비하고 검증을 통과한 콘텐츠를 예약 게시 |
| 검토 후 게시 | 생성 후 검토 대기, 승인한 revision만 게시 |
| 게시만 자동 | 사용자가 글·이미지를 등록하고 앱은 분할·예약·게시 수행 |

글 생성과 이미지 생성은 독립적으로 켜고 끌 수 있다. 이미지 없이 텍스트만 자동 생성하거나, 직접 작성한 글에 AI 이미지만 붙이는 조합도 지원한다.

승인 후 원문·게시 부분·이미지를 바꾸면 승인을 무효화한다. 예약이 이전 승인 revision을 유지할지 새 revision으로 바꿀지 명확히 보여주며, 미승인 변경분을 자동 게시하지 않는다.

### 4.2 생성 시점

| 방식 | 필수 동작 |
|---|---|
| 게시할 때 | 예약 시각에 생성 시작. 실제 게시 시각이 늦어질 수 있음을 표시 |
| 버튼을 눌렀을 때 | 1·5·20개 또는 직접 수량을 선택해 생성. 기본은 저장까지 |
| 미리 자동 생성 | 다음 세부 정책 중 하나를 주 전략으로 선택 |

미리 생성 정책:

1. **매일 지정 시각:** 지정된 현지 시각에 다음 날 또는 선택한 확보 기간의 예약 부족분 준비.
2. **예약 전 N분:** 각 예약의 예정 시각에서 N분 전 생성 시작.
3. **재고 부족 시:** 준비 완료·미배정 수량이 임계치 미만이면 목표 재고까지 보충.

첫 운영 시작, 가까운 예약 추가 시 정기 생성까지 기다리지 않고 부족분을 채우는 옵션을 제공한다. 전략은 중복 실행되지 않도록 구분하고 정책 버전을 저장한다.

### 4.3 부족분과 생성 작업

- 사용자 준비 자료와 이미 준비된 콘텐츠 중 자동 배치에 적합한 항목을 먼저 사용한다.
- 미완성 초안·미승인 글은 준비 완료 수량에 넣지 않는다.
- 예약 20개에 준비된 콘텐츠 8개가 있으면 생성 대상은 12개다.
- 이미 배정된 콘텐츠는 다른 예약에 중복 배정하지 않는다.
- 진행 중인 생성 작업과 확보된 생성 자리도 부족분 계산에 반영한다.
- 같은 예약 또는 같은 기간·정책의 생성 요청에 고유키를 부여해 동시 보충 중복을 막는다.
- 확보 기간 상한, 일일 생성 한도, 재생성·재시도 상한을 둔다.
- “생성하기”와 “지금 게시”를 분리한다. “생성 후 빈 예약에 배치”는 별도 선택이다.
- 예약 카드에 게시 예정 시각, 생성 예정 시각, 준비 상태를 따로 표시한다.
- 생성 실패·이미지 실패 시 설정된 정책 없이 불완전한 콘텐츠를 게시하지 않는다. 텍스트만 게시 대안은 사용자가 선택한 경우에만 적용한다.
- 선택 항목 취소·대기 작업 취소는 가능하되 이미 시작된 외부 과금 요청이 취소된다고 보장하지 않는다.
- 원격 생성 결과는 구조화된 스키마로 검증하고, 모델 출력에 포함된 명령을 시스템 명령으로 실행하지 않는다.
- 실제 AI 공급자 어댑터와 목업을 분리한다. 모델 이름·지원 옵션·단가는 구현 시 공식 문서로 확인하고 설정으로 관리한다.
- 브라우저의 ChatGPT 로그인 세션을 자동 조작하는 구조로 만들지 않는다.

## 5. 본문·자기 답글 분할과 게시

### 5.1 분할 모드

1. **기본 두 부분:** 전체 시나리오를 절반 부근의 문장·문단 경계로 나누어 본문 + 답글 하나로 구성.
2. **길이 초과 시만:** 가능한 내용을 본문에 배치하고 제한을 넘는 나머지를 답글로 연결.
3. **직접 나누기:** 편집기에서 분할 위치 또는 구분자로 본문·답글 지정.

두 부분 모드에서도 각 부분이 게시 제한을 넘으면 추가 답글로 나눈다. “답글 1개”는 기본 목표이며 모든 원문을 강제로 두 글 안에 넣는다는 뜻이 아니다.

- “기본 답글 1개 → 분량 초과로 실제 답글 3개”처럼 이유와 최종 개수를 표시한다.
- 문장·문단 우선, 불가피할 때 문자소 경계에서 나누고 이모지·URL을 중간에서 끊지 않는다.
- 원문을 별도 보관하고 누락·중복 없이 모든 내용을 유지한다.
- 공백·줄바꿈·정규화 처리 규칙을 문서화한다. 게시용 정규화와 원본 보존을 구분한다.
- 자동 분할에서 AI가 조용히 요약하거나 결말을 바꾸지 않는다.
- 최대 답글 수를 사용자가 제한했다면 초과 시 수정 대기로 둔다. 요약은 명시적으로 선택한 별도 동작이다.
- 1/N 번호 표기는 선택이며 추가되는 번호도 길이 계산에 포함한다.
- 사용자가 의도한 문맥 단절·후반부 시작 위치를 수정할 수 있다.

### 5.2 글자 수

X의 가중 글자 계산과 연결 계정의 실제 게시 능력을 반영한다. 일반 게시의 가중 280 제한, CJK·이모지·인식된 URL 규칙은 공식 문서와 twitter-text 적합성 사례를 기준으로 검증한다. 한글 글자 수를 무조건 280자로 허용하거나 Go len/단순 rune 개수/JavaScript string.length만 사용하지 않는다.

프론트 미리보기와 Go 서버 최종 검증이 같은 결과를 내야 한다. 프론트만 검사하고 서버를 생략하지 않는다. Go 구현은 검증된 라이브러리 또는 공식 적합성 fixture를 통과하는 구현을 선택한다. 운영 Node 서버를 글자 계산 때문에 추가하지 않는다.

장문 게시를 지원하는 계정인지, 해당 API에서 가능한지 확인한다. 모든 계정에 장문이 된다고 가정하거나 웹 화면의 길이를 API 권한으로 추정하지 않는다. 확인되지 않으면 표준 모드를 기본으로 두고 지원 설정을 명시한다.

### 5.3 게시 순서

- 본문 게시 성공 → 반환된 X post_id 저장 → 그 ID에 자기 답글 게시.
- 여러 답글이면 직전 부분의 ID에 이어 붙여 순서 있는 타래를 만든다.
- 본문·답글은 API상 정확히 동시에 생성되는 것이 아니다. 본문 ID를 받은 후 순차 실행한다.
- 5분 뒤 임의로 새 글을 검색해 본문을 추측하는 방식으로 구현하지 않는다.
- 묶음 사이 30분 간격과 같은 묶음 안의 답글 간격은 독립된 설정이다.
- 부분별 전송 의도·시도·성공 ID를 저장한다. 본문만 성공하면 “일부 완료”로 표시한다.
- 답글 실패 시 이미 성공한 본문을 다시 올리지 않고 실패 부분부터 이어 간다.
- 미디어는 먼저 X에 파일로 업로드하고 반환된 media_id를 게시 요청에 첨부한다.
- 연결 권한, 현재 X API의 자기 타래 지원 조건, 미디어 제한, 유료 정책을 구현 시 확인한다. 호출 불가를 감추거나 비공식 우회로 대체하지 않는다.

## 6. 예약·시간표

### 6.1 기본 규칙

- 기본 시간대 Asia/Seoul. DB 시각은 timestamptz/UTC로 저장하고 시간대·정책을 별도 보관한다.
- 요일별 여러 허용 구간을 제공한다. 기본 사용 의도는 새벽과 낮이다.
- 시간 구간은 시작 포함·끝 제외로 일관되게 처리한다.
- 월요일 23:00~03:00은 월요일 밤에서 화요일 새벽까지 이어지는 구간으로 해석하고 UI에 표시한다.
- 겹치는 구간은 중복 등록을 막거나 정규화해 계산한다. 중복 슬롯을 만들지 않는다.
- 하루 20묶음은 **한국 시간 날짜별 새 본문 게시 수의 기본 목표·상한**이다. 답글 수는 별도 집계한다.
- 재시도·남은 답글 이어 쓰기를 새 묶음으로 중복 집계하지 않는다.
- 앱 밖에서 사용자가 X에 직접 게시한 글은 이 수량에 자동 포함하지 않는다.
- 요일별 켜기/끄기, 특정 날짜 제외, 오늘만 쉬기, 전체 자동 운영 일시정지를 지원한다.

### 6.2 30분 + 추가 랜덤 지연

~~~text
다음 예약 시각 = 이전 예약 시각 + 기본 간격 + 추가 랜덤 지연

예: 기본 30분, 추가 지연 0~5분
12:00 → 12:33 → 13:04 → 13:39
~~~

- ±랜덤이 아니다. 위 예시의 묶음 간격은 30~35분이다.
- 12:00·12:30·13:00에 각각 독립 지연을 더해 실제 간격이 25분으로 줄어드는 방식으로 만들지 않는다.
- 첫 슬롯은 허용 구간 시작을 기준으로 하되 직전 예약과 최소 간격, 현재 시각, 고정 예약을 반영한다.
- 시각과 랜덤값은 시간표 생성 시 한 번 확정해 DB에 저장한다.
- 새로고침·재시작·재시도 때문에 랜덤값을 다시 뽑지 않는다.
- 구간 밖이면 다음 허용 구간으로 이동하고 이전 슬롯과의 최소 간격도 유지한다.
- 테스트에서는 시계·난수 생성기를 주입해 결정적으로 검증한다.
- 일일 요청 수량을 넣을 수 없으면 배치 가능 수·부족 수·해결 옵션을 보여준다. 간격을 줄이거나 허용 시각을 넘겨 억지로 채우지 않는다.
- 실제 지연으로 직전 본문 게시와 다음 본문 게시가 가까워지면 다음 미실행 예약을 늦춰 최소 간격을 보장한다. 원래 예정 시각·지연 사유·새 시각을 기록하고, 랜덤을 새로 뽑지 않는다.
- 랜덤 간격을 계정 제한 회피나 제재 방지 보장으로 설명하지 않는다.

### 6.3 편리한 시간 설정

- “새벽”, “낮” 시간 구간 카드에 시작·종료·적용 요일을 입력하고 + 버튼으로 구간 추가.
- 하루 묶음 수, 기본 간격, 추가 지연 범위만으로 시간표 자동 만들기.
- 적용 전 실제 예약 목록·구간별 수량·예상 X 게시물 수 미리보기.
- 날짜별 타임라인과 간단한 주간 보기.
- 콘텐츠 여러 건 선택 → 다음 빈 시간에 배치.
- 순서 바꾸기, 내일로 이동, 다음 빈 시간, 예약 해제.
- 개별 날짜·시간 지정과 “시간 고정”. 고정 예약은 전체 재배치에서 유지.
- 평일 설정 복사·요일별 일괄 적용.
- 설정 변경 시 영향을 받는 미래 예약을 보여주고 적용 범위를 선택.
- 이미 게시 중이거나 완료한 예약을 재배치하지 않는다.
- 게시량을 줄여 남는 콘텐츠는 보관함에 유지한다.
- 일정 수정만으로 글·이미지를 다시 생성하지 않는다.
- 기본은 허용 구간과 간격을 따르며, 개별 고정 시각 충돌도 숨기지 않는다.
- 사용자가 직접 누르는 “지금 게시”는 자동 시간표와 구분한다. 허용 구간·간격 밖이라면 경고와 명시적 확인 후 수동 예외로 기록하며 기존 예약을 중복 실행하지 않는다.

### 6.4 미준비·시간대 종료·다운타임

- 콘텐츠 미준비·검토 미승인·이미지 실패이면 자동 게시하지 않고 지연 상태와 원인을 표시한다.
- 기본 복구는 다음 빈 허용 슬롯으로 이동이다. 다음 날에도 그날 수량 상한을 적용한다.
- 준비된 다른 콘텐츠로 대체하는 옵션은 명시적으로 선택한 경우에만 사용한다.
- 게시 시각 생성 모드에서 생성 완료 시 허용 구간이 끝났다면 다음 허용 시간으로 옮긴다.
- 자동 X 게시 요청을 시작할 때마다 허용 시간대를 확인한다.
- 구간 종료 직전에는 설정된 답글 간격과 여유 시간을 고려해 새 묶음을 시작하지 않는다.
- 그래도 남은 답글이 구간 밖으로 넘어가면 “남은 답글 예약됨”으로 표시하고 다음 허용 구간에서 이어 간다. 이미 보낸 요청의 응답 도착 시각까지 통제한다고 약속하지 않는다.
- 서버 복구 직후 밀린 예약을 한꺼번에 게시하지 않는다. 기존 성공 기록을 보존하고 미래 허용 시간으로 재배치한다.
- 전역 일시정지는 새 외부 게시 요청 시작을 막는다. 이미 전송한 요청은 되돌릴 수 없으며 결과를 저장한다.
- 생성 일시정지와 게시 일시정지를 별도로 제공한다.

## 7. 이미지와 R2

### 7.1 이미지 기능

- AI 이미지 생성, 직접 업로드, 이미지 없이 게시.
- 글 내용에서 이미지 프롬프트 초안 만들기와 직접 수정.
- 모델·품질·비율·스타일·개수 선택, 저장된 기본값.
- 생성 결과 선택·부분 재생성·교체·삭제·정렬·기본 자르기.
- 본문 또는 특정 답글에 이미지 배치, 각 게시 부분의 첨부 제한 확인.
- 이미지 보관함에서 기존 이미지 재사용·검색·다운로드.
- 업로드·생성 중 진행 상태, 실패 원인, 재시도.
- 썸네일·원본과 관련 파일의 관계를 보관하고 정리할 때 함께 처리.
- 파일 형식·크기·해상도·실제 내용 검사, 서버가 안전한 객체 키 생성.
- 임의 URL 가져오기는 초기 필수가 아니다. 제공한다면 SSRF·다운로드 크기·허용 목적지를 제한한다.

### 7.2 R2 공개 조회

사용자는 **R2 이미지 URL의 공개 조회를 허용**했다. 앱 관리 기능의 인증과 별개다.

- 이미지 파일은 R2, 객체 키·크기·형식·해시·사용 관계·게시 시각은 PostgreSQL.
- 앱 전용 버킷 또는 x-automation/ 같은 전용 접두사를 사용한다.
- 사용자가 예시로 보여준 다른 서비스의 /admin/ 경로와 파일을 그대로 사용하거나 정리하지 않는다.
- R2_PUBLIC_BASE_URL로 공개 주소를 구성하고 실제 사용자 예시 URL을 코드에 하드코딩하지 않는다.
- 공개 이미지 URL은 로그인 없이 접근 가능하다. /admin/ 또는 UUID가 접근 인증을 제공하는 것은 아니다.
- 미게시 이미지도 URL을 아는 사람에게 공개될 수 있는 저장 방식임을 설정 도움말에 짧게 표시한다.
- 쓰기·삭제·목록 관리 API는 Go 서버를 거치며 인증을 적용한다. R2 쓰기 키는 브라우저에 제공하지 않는다.
- 운영용 공개 도메인을 설정할 수 있어야 한다. r2.dev는 개발용이며 운영 트래픽 제한을 고려한다.
- Go가 R2에서 파일을 읽어 X에 업로드한다. R2 URL을 게시 본문에 붙이는 것으로 이미지 첨부를 대체하지 않는다.
- 공개 버킷 전체의 정책·수명주기·다른 서비스 파일을 자동 변경하지 않는다.

### 7.3 게시 후 14일 정리

**업로드 날짜가 아니라 마지막 성공 게시 완료 시각을 기준으로 한다.**

1. 이미지가 포함된 X 게시 부분의 성공 시각을 기록한다.
2. 해당 묶음의 게시가 완료되면 이미지 보관 기준을 묶음 완료 시각까지 갱신한다. 부분 실패 상태에서는 활성 참조로 보호한다.
3. 이미지가 여러 묶음에서 재사용되면 가장 최근 성공 사용·완료 시각을 기준으로 보관 기간을 다시 계산한다.
4. 매일 정리 작업이 기준 시각 + 보관 기간을 지난 이미지를 조회한다.
5. 초안·예약·게시 중·재시도·결과 확인 필요 상태에서 쓰는 이미지는 제외한다.
6. 한 번도 게시하지 않은 이미지는 이 14일 규칙으로 지우지 않는다.
7. 삭제 대상으로 선점한 이미지에 새 참조가 생기지 않도록 트랜잭션과 deleting 상태로 보호한다.
8. R2 삭제 성공 또는 이미 없음이 확인되면 DB에 deleted_at을 기록한다.
9. 실패하면 재시도 가능 상태와 내부 알림을 남긴다.
10. 이미지 메타데이터, 원문, 게시 기록, X 링크는 유지한다. 앱 미리보기에는 “보관 기간이 지나 정리된 이미지”를 표시한다.

정확히 14일이 되는 초에 삭제를 보장하는 기능은 아니다. 매일 검사하므로 14일 경과 후 다음 정리 실행 때 삭제한다. 운영 설정에서 보관 일수를 변경할 수 있다.

R2 원본 정리는 이미 X에 업로드한 첨부 이미지를 삭제하는 동작이 아니다. 커스텀 도메인 CDN 캐시가 있으면 캐시 만료·삭제 정책도 문서화한다.

R2에 업로드됐지만 DB 연결에 실패한 고아 파일은 별도로 식별한다. 앱 전용 접두사 안에서 유예 기간·참조 확인을 거쳐 처리하고, 버킷 전체를 일괄 삭제하지 않는다. R2의 업로드 경과일 기준 수명주기로 게시 후 14일 규칙을 대신하지 않는다.

## 8. 비용과 앱 내부 알림

### 8.1 비용 최소화

- 텍스트 생성·이미지 생성·X 게시·저장/서버 비용을 구분한다.
- 앱이 측정한 사용량과 추정 비용, 외부 청구서의 실제 결제액을 혼동하지 않는다.
- 모델·품질·이미지 수를 선택하고 생성 전 예상 사용량을 보여준다.
- 분할 결과가 바뀌면 실제 X 게시물 수와 게시 예상 비용을 갱신한다.
- 텍스트만, 수동 작성 + 게시만, 이미지 직접 업로드 모드를 제공한다.
- 부족분만 생성하고 생성 완료 콘텐츠를 일정 변경 때문에 다시 만들지 않는다.
- 일일 생성량·재생성 횟수·동시 작업 수를 제한해 실수로 대량 호출하지 않게 한다.
- 선택적 월 한도와 한도 도달 정책: 생성만 중지 / 신규 게시까지 중지.
- 한도를 켰다면 실행 전 추정 비용을 예약하고 완료 후 사용량을 정산한다.
- 여러 워커가 동시에 한도를 통과해 초과하지 않도록 비용 예약도 DB에서 처리한다.
- 묶음 중간에 내부 한도에 걸려 답글을 끊지 않도록 시작 전 전체 타래 예상 비용을 확보한다. 외부 잔액 부족은 별도 오류로 처리한다.
- 재시도 시 성공한 게시를 다시 비용 처리하지 않는다. 실패한 요청도 공급자에 따라 과금될 수 있으므로 확정되지 않은 비용은 구분한다.
- API 단가·환율·가격 확인일을 설정 또는 버전 있는 요율 데이터로 관리한다.
- 현재 X의 URL 포함 게시 등 별도 과금 조건이 있다면 반영한다. 정확하지 않은 고정 “게시당 몇 원”을 표시하지 않는다.
- 최소 비용이라는 이유로 무조건 무료라고 안내하지 않는다. 실제 단가 확인 전 예상 금액을 꾸며내지 않는다.

### 8.2 알림

알림 채널은 앱 내부만 구현한다. 텔레그램·이메일·브라우저 푸시를 추가하지 않는다.

- 상단 알림 아이콘과 읽지 않은 개수.
- 생성 실패, 게시 실패·일부 완료, 인증 만료, 콘텐츠 부족, 예산 한도, 이미지 정리 실패.
- 정리 성공·일괄 생성 완료 등은 낮은 중요도의 묶음 알림.
- 같은 원인의 반복 실패는 묶어서 갱신해 도배를 막는다.
- 읽음/모두 읽음, 알림에서 해당 콘텐츠·연결 설정·재시도 화면으로 이동.
- 잠깐 보이는 토스트와 지속적으로 남는 알림함을 구분한다.
- 브라우저를 닫아도 서버 작업과 알림 저장은 계속한다. 다시 접속하면 누적 상태를 표시한다.
- 웹을 닫은 사용자에게 실시간 전달됐다고 보장하지 않는다. 서버 자체가 내려간 경우의 감지는 KoDeploy 상태 확인 영역이다.

- 자주 쓰는 값만 먼저 보여주고 고급 정책은 펼쳐서 설정한다.
- 입력 레이블을 유지하고 placeholder만으로 의미를 전달하지 않는다.
- 시간·수량은 적절한 모바일 입력 방식, 오류는 해당 입력 옆에 표시한다.
- 주요 화면마다 가장 중요한 버튼 하나를 명확히 한다.
- 일괄 취소·삭제·재배치처럼 영향이 큰 작업은 대상 수와 영향을 보여준다.
- 생성 취소, 저장 복구, 되돌리기 등 가능한 작업에는 회복 경로를 제공한다.
- 정렬은 드래그 외에 위/아래 이동 버튼과 키보드 조작도 가능하게 한다.
- 빈 상태는 “아직 글이 없어요”와 생성/직접 등록 버튼을 제공한다.
- 로딩·생성 중·저장 중·오류·권한 없음·연결 끊김·비활성 이유를 설계한다.
- 네트워크 단절 상태에서 저장·게시 성공으로 표시하지 않는다.
- 데모 데이터는 데모 배지와 분리된 데이터 영역으로 표시한다. 운영 수치를 하드코딩하지 않는다.
- WCAG 수준의 대비·포커스·레이블·모달 포커스 이동을 확인한다.
- 360/390/768/1440px에서 점검하고, 라이트·다크 모두 가로 넘침·고정 UI 가림·키보드 문제를 검사한다.

## 10. 서버와 코드 구조

### 10.1 단순한 모놀리스

Go 프로세스 하나가 HTTP, 정적 프론트 제공, 예약 워커, 생성 워커, 이미지 정리를 담당한다. PostgreSQL을 영속 데이터·작업 큐 저장소로 사용한다. Redis, Kafka, RabbitMQ, 별도 운영 Node 서버는 기본 의존성으로 추가하지 않는다.

프론트는 React + TypeScript + Vite 정적 빌드로 구성한다. 빌드 결과를 Go embed.FS에 포함하고 같은 origin에서 제공한다. 프론트 빌드 후 Go를 빌드한다. 개발 환경에서만 Vite 개발 서버와 API 프록시를 사용한다.

Go는 net/http 또는 가벼운 라우터, pgx 계열 DB 접근, 버전 있는 SQL 마이그레이션을 기본으로 한다. 현재 지원되는 안정 버전을 공식 자료로 확인하고 의존성 버전·lockfile을 고정한다.

권장 구조이며 기존 코드가 있으면 합리적으로 조정할 수 있다.

| 경로 | 책임 |
|---|---|
| cmd/server | HTTP·워커 시작, 종료 처리 |
| cmd/admin | 비밀번호 해시 생성 등 운영 보조 명령 |
| internal/config | 환경변수 검증 |

## 11. 인증과 보안

### 11.1 한 명만 로그인

- ADMIN_USERNAME과 Argon2id 등 적절한 ADMIN_PASSWORD_HASH를 서버 설정으로 받는다.
- 안전한 비밀번호 해시 생성 CLI를 제공한다. 평문 비밀번호를 소스·프론트·샘플 파일에 넣지 않는다.
- 운영 모드에서 인증 필수값이 없으면 시작을 거부한다. 인증을 자동 해제하거나 공용 기본 비밀번호를 제공하지 않는다.
- 회원가입·공개 비밀번호 초기화·사용자 추가 화면을 만들지 않는다.
- 서버 세션, 충분한 무작위 세션 ID, Secure·HttpOnly·SameSite 쿠키, 만료·로그아웃 무효화.
- 로그인 시도 제한, 세션 재발급, 상태 변경 요청의 CSRF 방어.
- 로컬 HTTP 개발 예외는 명시적인 개발 모드에서만 허용한다.
- X OAuth 콜백과 SameSite 설정을 함께 검증한다. OAuth state·PKCE·만료·재사용 방지를 구현한다.

### 11.2 보호 범위

- 페이지에서 로그인 화면을 보여주는 것만으로 보안을 끝내지 않는다.
- 콘텐츠·프롬프트·예약·설정·내보내기·이미지 업로드/삭제·게시 API에 서버 인증을 적용한다.
- 로그인에 필요한 정적 파일·로그인 진입점·최소 health 응답 등 공개 경로를 명시적으로 한정한다.
- 공개 R2 이미지 조회는 합의된 예외다. 앱의 업로드/삭제 권한과 혼동하지 않는다.
- API의 401/403/404를 SPA index.html로 반환하지 않는다.
- OAuth 콜백은 경로가 접근 가능하더라도 유효한 연결 시작 세션과 state 검증 없이 연결을 변경할 수 없다.
- AI가 만든 텍스트도 HTML로 신뢰하지 않는다. 안전한 텍스트 렌더링을 기본으로 한다.
- origin·프록시 신뢰 범위를 설정하고 로그인 제한을 임의 헤더로 우회할 수 없게 한다.
- 민감한 응답은 적절한 cache-control을 적용한다.

### 11.3 비밀정보

- X·AI·R2 키는 서버 전용 환경변수 또는 Secret에 보관한다.
- 갱신 가능한 X 토큰 등 DB에 필요한 비밀은 서버의 안정적인 암호화 키로 암호화한다.
- TOKEN_ENCRYPTION_KEY는 재배포마다 새로 생성하지 않는다. 변경·백업 절차를 문서화한다.
- 설정 화면은 연결 여부·마스킹된 정보만 반환한다.
- VITE_ 등 브라우저 번들에 들어가는 환경변수에 비밀값을 넣지 않는다.
- 토큰·비밀번호·완전한 인증 헤더·사용자 원문을 일반 로그에 남기지 않는다.
- 로그의 오류 메시지에 공급자 응답의 비밀정보가 섞이지 않도록 정리한다.

## 12. 무인 운영·실패 복구

### 12.1 DB 작업 선점

- 작업 생성에 비즈니스 고유키를 두어 같은 예약·revision·게시 부분이 중복 실행 작업으로 만들어지지 않게 한다.
- PostgreSQL의 짧은 트랜잭션과 FOR UPDATE SKIP LOCKED 등을 이용해 작업을 선점한다.
- lease_owner, lease_expires_at, lease_version을 기록하고 장기 작업은 갱신한다.
- 외부 API 응답을 기다리는 동안 DB 트랜잭션을 오래 잡지 않는다.
- 결과 저장 시 여전히 소유자인지 검증하고, 소유권을 잃은 워커는 새 외부 호출을 시작하지 않는다.
- 롤링 배포 중 잠깐 인스턴스 두 개가 겹쳐도 동작해야 한다.
- replicas=1만으로 중복 방지가 해결된다고 가정하지 않는다.
- 단일 계정의 본문 게시 시작 순서와 최소 간격도 DB 수준에서 조정한다.

### 12.2 외부 요청의 불확실성

**DB 고유키와 lease만으로 X 외부 게시가 정확히 한 번 실행된다고 보장할 수 없다.**

- 전송 전에 요청 의도를 기록하고 성공 응답의 ID를 즉시 저장한다.
- 응답이 끊겨 실제 게시 성공 여부가 불명확하면 unknown/“결과 확인 필요”로 둔다.
- 이 상태를 단순 실패로 보고 다시 게시하지 않는다.
- 현재 API가 멱등성 키를 지원하는지 확인하고 지원 범위 안에서만 사용한다.
- 권한·비용이 허용하는 안전한 조회로 확인하거나, 사용자가 실제 게시 URL/ID를 연결해 해결할 수 있게 한다.
- 사용자가 확인 후 재시도를 선택할 수 있는 절차를 제공하되 중복 가능성을 숨기지 않는다.
- 오래된 lease 회수 후에도 전송 중이던 작업을 무조건 pending으로 돌리지 않는다.
- 생성 API도 과금된 결과가 불명확할 수 있다. 재시도 상한과 결과 확인 상태를 적용한다.

### 12.3 재시도와 종료

- 실패 유형을 재시도 가능·설정 수정 필요·검토 필요·결과 불명확으로 구분한다.
- 429는 Retry-After 등 공급자 제한을 따르고 일시 오류는 제한된 backoff를 적용한다.
- 인증 만료·잘못된 콘텐츠·권한 부족은 무한 재시도하지 않는다.
- 게시·생성·업로드별 타임아웃·최대 시도 수·동시 실행 수를 설정한다.
- 모든 게시 재시도에도 허용 시간 구간과 부분 성공 기록을 적용한다.
- SIGTERM 시 신규 선점을 멈추고 진행 작업의 결과를 저장하며 종료 유예 시간 안에 정리한다.
- 재시작하면 DB 상태에서 이어 간다. 프로세스 메모리의 cron 목록만 신뢰하지 않는다.
- 예약 취소·즉시 게시·자동 실행이 경쟁해도 한 실행만 활성화되도록 상태 전이를 원자적으로 처리한다.

## 13. KoDeploy와 서버 세팅

### 13.1 배포 산출물

- 멀티 스테이지 Dockerfile: 프론트 빌드 → Go 빌드 → 최소 실행 이미지.
- 실행 이미지에 프론트 산출물을 별도 Node 서버 없이 Go와 함께 제공한다.
- non-root 사용자, CA 인증서, Asia/Seoul 등 시간대 데이터, 종료 신호 처리.
- Linux ARM64를 포함해 배포 가능하게 하고 amd64 환경도 검증한다. 네이티브 의존성을 쓴다면 교차 빌드·실행 조건을 기록한다.
- PORT 환경변수를 받아 0.0.0.0에 바인딩. 제안 기본값은 8080이며 실제 KoDeploy 규약을 확인한다.
- /healthz는 생존 확인, /readyz는 DB·마이그레이션 준비 확인. 공개 응답에 비밀·상세 설정을 노출하지 않는다.
- 일시적인 X·AI 장애가 앱 컨테이너 재시작 루프를 만들지 않게 한다.
- 로컬 PostgreSQL compose, .env.example, Makefile 또는 동등한 실행 스크립트.
- 필요하면 로컬 S3 호환 저장소나 명시적인 테스트 저장소를 개발 전용으로 제공한다.
- 실제 게시와 분리된 목업 프로필을 제공한다. 운영에서 키 누락 때문에 자동으로 목업 성공으로 전환하지 않는다.

9. 운영자가 실제 게시 허용을 설정하고 앱에서 자동 운영 시작.
10. 재배포, 일시정지, 장애 복구, DB 백업·복원, 토큰 키 보관.

KoDeploy의 존재하지 않는 CLI·배포 설정 파일을 지어내지 않는다. 실제 환경 접근이 없으면 확인해야 할 항목을 문서에 표시하고 컨테이너로 검증 가능한 범위를 끝낸다.

DB 마이그레이션은 버전과 동시 실행 잠금을 사용한다. 운영 데이터 초기화·파괴적 마이그레이션을 자동 실행하지 않는다. 재배포 시 예약·게시 ID·키·이미지가 사라지지 않도록 컨테이너 로컬 디스크에만 저장하지 않는다.

main 푸시가 자동 배포를 유발할 수 있으므로 처음부터 미완성 서버가 실제 게시를 시작하지 않는 기본 상태를 유지한다.

테스트는 정책과 실패 복구에 집중한다. 구현을 그대로 복사한 무의미한 테스트나 시각적 작은 수정마다 과도한 테스트를 만들지 않는다. 관련 검증이 통과하면 새로운 실패·변경·의문이 없는 한 반복 실행으로 진행을 늦추지 않는다.

## 17. 실행 명령과 산출물 계약

프로젝트를 만든 뒤 아래 명령 또는 동등한 명령이 동작하도록 구성하고 README에 정확히 적는다. 명령은 이 문서 작성 시 이미 존재한다는 뜻이 아니라 구현할 개발 인터페이스다.

~~~bash
make setup
make dev
make test
make lint
make build
make e2e
make docker-build
~~~

- setup: 의존성·개발 설정 안내. 비밀을 임의 생성해 커밋하지 않는다.
- dev: 로컬 DB와 프론트/API 개발 실행. 여러 터미널이 필요하면 분리 명령도 문서화.
- test: 의미 있는 Go·프론트 테스트. DB 통합 테스트 조건 명시.
- lint: Go 정적 검사·프론트 타입/lint.
- build: 프론트 빌드 후 Go embed 바이너리 생성.
- e2e: 테스트 DB·목업 공급자·브라우저로 핵심 흐름 검증.
- docker-build: 배포 이미지 빌드, 대상 아키텍처 옵션.

최종 README에는 다음을 포함한다.

- 무엇을 하는 앱인지와 실제 화면 예시.
- 최소 실행·로그인 설정·프롬프트 입력·시간표 설정.
- 게시만 자동으로 쓰는 방법과 완전 자동으로 바꾸는 방법.
- 생성 시점과 게시 시점 차이.
- 콘텐츠 묶음과 X 게시물 수 차이.
- R2 공개 이미지와 게시 후 정리 기준.
- 일시정지·실패한 답글 재개·결과 확인 필요 해결.
- 예상 비용의 한계와 현재 가격 확인 경로.
- main 배포·실게시 활성화·중지·복구.
- 구현 완료와 외부 자격증명 때문에 아직 검증하지 못한 항목의 구분.
